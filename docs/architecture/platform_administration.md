# 平台管理架构

本文定义 `/admin` 的全局资源边界、信息架构和管理关系。平台管理不是租户工作台的放大版，而是面向 `super_admin` 的全局控制面。

## 资源关系

平台管理以 `统一腾讯接入 → 腾讯企业 → 内部租户投影 → 用户与品牌权限` 为唯一启用流程：

- 平台只维护一组固定 Tencent TeamID 和一个加密 API Key，系统直接使用已接入 OpenAPI；
- 腾讯品牌来自固定 TeamID 的上游目录，BrandID 全局只能对应一个平台企业；
- 首次保存配置时，系统一次完成腾讯验证、已有品牌导入和企业投影；之后通过官方接口创建品牌时立即生成投影，Worker 每日核对腾讯完整目录，且启动时仅在最近 20 小时无成功核对时补查，腾讯企业页面每 60 秒刷新本地投影；不提供独立的本地企业创建流程；
- 企业是成员、权限、双余额和业务数据的内部租户边界，腾讯 BrandID 是企业的上游来源与资源范围；两者一一对应但仍保留不同主键和职责；
- 首次创建投影时，配置或创建操作者作为初始 `tenant_admin`，之后可从企业详情增加或转移管理员；
- 每家企业保留一条相同 TeamID 的本地 `answerbit_team_bindings` 及托管连接占位记录，以承接现有业务外键和调用日志，但不复制平台统一密钥；该记录是实现细节，不是可管理、可授权或可展示的业务资源；
- `tenant_admin` 自动管理本企业绑定品牌，其他成员通过 `brand_access` 获得该 BrandID 的角色范围；
- `account_type` 只表达管理员、代理商和客户的运营类型，实际授权由平台角色、企业成员角色、按企业功能 allowlist 和品牌范围共同决定。

## 管理控制面

`/admin` 使用独立资源中心组织能力：

1. **运营总览**：接入完成后的默认入口，聚合腾讯企业、有效用户、成员关系、24 小时 AnswerBit 失败率与 P95、Worker 在线实例、五项周期任务、文章/报告队列与通知规则健康、统一接入状态及账户结构，并提供最近操作审计和 AnswerBit 调用时间线；总览只组合现有只读资源，不建立第二份统计状态；
2. **腾讯服务**：平台启用的第一步，配置或轮换固定 TeamID 与统一 Key，并查看掩码、验证结果和腾讯品牌目录同步状态；
3. **发布平台**：只负责外部发布供应商接入，验证并加密保存小青蛙统一 API Key，查看上游余额、算力和最近连通性，不混放渠道经营和订单操作；
4. **企业与品牌**：只查询腾讯目录生成的企业投影，支持按名称/内部标识与状态服务端筛选，直接通过腾讯接口新增、编辑或删除企业，查看 BrandID、成员和接入范围，冻结或恢复企业，配置成员状态与角色；
5. **客户与代理**：按姓名、账号、状态和账户类型查询全局账户，维护客户等级与利润策略，通过独立弹窗创建身份，在客户与代理商之间切换类型，设置代理商有效时间与企业/品牌/腾讯积分额度，并逐企业配置功能授权范围，查看企业与品牌权限，启用或停用账户；
6. **资产与计费**：管理员向企业积分或人民币发布账户人工入账，维护业务功能积分规则，并跨企业查看可按用户、资产和操作类型筛选的积分与余额流水；平台不维护品牌套餐或按套餐限制企业；
7. **腾讯用量**：跨企业选择固定 TeamID 下的品牌范围，查看当前订阅、可用积分、积分批次、周期配额、消耗趋势、品牌排行、积分流水、订阅日志和配额调整；提供“用积分扩容 · 监控品牌”，确认后直接调用腾讯官方增购接口，最终扣减和配额以重新读取的腾讯计量为准；
8. **发布渠道**：维护聚合与人工渠道。目录区分上游采购成本、上游接单状态、平台上下架与四级售价，并允许分类筛选、固定等级售价和平台上下架；普通用户、铜牌代理、银牌代理与金牌代理的全局加价和积分系数仍在“客户与代理”维护；
9. **发布订单**：聚合订单由上游自动履约并同步状态，人工订单由管理员推进处理、填写交付链接；失败或确认取消后按订单价格快照退回发布余额；
10. **运行与审计**：先展示 Worker 心跳、计费维护、异步任务恢复、持续检测、腾讯企业同步、聚合发布同步、文章/报告队列、通知规则评估和 24 小时 AnswerBit 失败率，再查询平台操作审计和 AnswerBit 业务调用健康；周期任务卡展示最近成功、耗时、状态和错误码。审计支持按操作、资源或 Request ID 搜索以及结果筛选，调用健康支持按 operation、requestId、错误码、企业或操作用户搜索以及状态筛选。调用时间线同时展示所属企业和操作用户，空用户明确标识为系统任务。

左侧导航按“总览 → 服务接入 → 客户经营 → 业务运营 → 系统治理”组织，而不是按供应商名称堆叠功能。客户与代理管理先展示账户结构概览，再全宽展示“客户等级与利润策略”和用户目录。发布业务拆成“发布平台、发布渠道、发布订单”三个资源页，并在页首共享“接入平台 → 经营渠道 → 分配客户等级 → 跟踪订单”的业务链路。发布平台按“接入设置主栏 + 上游账户侧栏”排列；发布渠道展示可筛选目录并在底部新增人工渠道；发布订单独立展示自动或人工履约状态。资产与计费按“入账对象主栏 + 积分规则侧栏 → 用户流水 → 积分规则编辑”排列。常驻新增和编辑表单仍位于读取内容下方，不与主列表左右争用首屏宽度；窄屏统一顺序堆叠。

详情使用抽屉承载关系数据，企业、用户、审计和调用健康列表保持资源级服务端分页。企业、用户和品牌可互相定位，避免用一个混合表格表达多对多关系。集合 API 保留查询与状态筛选参数；调用健康可按 operation、requestId、错误码、企业或操作用户搜索。

平台管理外壳是单页客户端工作区。接入完成后，无 `section` 的 `/admin` 默认进入运营总览；左侧资源中心通过 `/admin?section=<resource>` 更新地址，不触发整页刷新，深链接以及浏览器前进/后退恢复当前资源中心。未接入时服务端强制进入 `integration`，其余资源继续锁定。运营总览并行读取 `/admin/overview`、统一接入配置以及最近五条审计和调用记录；各资源目录保留独立分页与筛选状态，刷新只重取当前模块需要的数据，快速切换模块或筛选时忽略先前请求的迟到结果。客户与代理管理在目录之前展示全局账户摘要和客户等级规则，筛选、分页和状态操作只刷新当前模块数据。

## 控制面分层与数据流

平台管理沿用 Web 后端统一分层，不从客户端直接访问数据库或腾讯接口：

```text
/admin client workspace
  -> readiness + session gate
  -> read APIs (overview / directories / timelines)
     -> Admin Service -> platform repositories -> PostgreSQL read models
  -> command APIs (configure / sync / create / update / grant / fulfill)
     -> permission + business preconditions
     -> repository transaction and/or AnswerBit gateway
     -> operation_logs + resource refresh
```

发布业务的数据与操作链路固定为：

```text
发布平台接入
  -> 验证并加密保存小青蛙 API 配置
  -> Worker 分页同步媒体目录到本地渠道缓存
  -> 管理员筛选渠道，设置平台上下架和四级售价
  -> 管理员在客户与代理页分配客户等级及全局利润规则
  -> 客户选取当前等级有效售价并提交订单
  -> 数据库事务重新计算售价、扣减发布余额并保存订单价格快照
  -> 聚合渠道自动投稿并轮询上游；人工渠道进入后台处理队列
  -> 成功记录交付链接；失败或确认取消时幂等退回价格快照金额
```

上游媒体目录只拥有采购成本、上游接单状态和媒体属性；平台拥有客户售价、平台上下架和客户可见性；订单拥有提交时价格快照与履约状态。三个状态域不互相覆盖，页面刷新只读取对应本地资源，目录同步与订单轮询由 Worker 执行。

运营总览是查询组合层：指标来自 `/api/v1/admin/overview`，接入状态来自统一配置资源，最近活动来自审计和调用集合的第一页，不缓存派生数字，也不承担任何写入。运行健康通过 `runtime_heartbeats`、`runtime_task_statuses`、文章/报告任务更新时间和通知规则最近评估字段实时推导：90 秒内有心跳才视为 Worker 在线；周期任务失败、超过自身超时阈值仍在运行、超过两个调度周期未成功或从未上报均标记异常；文章或报告 `queued` 超过 10 分钟、`running` 超过 15 分钟计为过期队列任务；启用规则存在评估错误或 30 分钟未评估也标记异常。总览和“运行与审计”页面每 30 秒自动刷新运行健康，页面隐藏或离线时暂停，恢复后立即补拉。企业、用户、审计和调用搜索统一使用集合资源的 `q`、`status` 与分页参数，筛选在 Repository 查询中完成；客户端只维护当前资源的查询状态。具有外部或财务副作用的操作继续走独立 Service，并在成功后刷新当前资源；页面消息不是成功依据，最终状态以服务端响应和审计记录为准。

## 权限与写入规则

- 所有 `/api/v1/admin/*` 端点先验证 Session，再通过 `requirePlatformPermission` 校验数据库角色权限；
- 固定 TeamID 与统一 Key 状态必须为 `active`，企业、用户、余额、发布、审计及租户业务才开放；接入前只允许读取或写入腾讯统一配置；
- 全局读取分别使用 `platform.tenant.read`、`platform.user.read` 或 `platform.answerbit.read`；
- 企业、成员、统一腾讯配置和品牌分配使用 `platform.tenant.manage`；
- 统一 Key 保存前实际调用 `/geo/query/brand` 验证 TeamID 与 Key；系统不再提供本地 operation 权限选择，最终授权以腾讯官方控制台为准；
- TeamID 首次配置并通过腾讯验证后即锁定，后续只允许轮换统一 Key；
- 首次配置或 Key 轮换通过 `/geo/query/brand` 验证固定 TeamID，并在同一流程导入已有 BrandID、补建企业投影和刷新连接健康；Worker 每日自动执行相同的目录核对，启动时按最近成功时间决定是否补查，腾讯企业页面自动刷新本地投影，不要求管理员反复操作；`POST /api/v1/admin/answerbit-enterprise-syncs` 仅保留为运维诊断资源，目录同步不扣减企业腾讯积分；
- 平台普通新建腾讯品牌必须先获得 `/geo/brand/create` 返回的 BrandID；附带初始化问题或竞品时改用固定 TeamID 调用 `/geo/brand/bundle/create`。两种流程都只在腾讯成功后写入目录并创建企业投影；腾讯失败时不产生本地品牌或企业；
- 平台修改或删除腾讯企业必须分别先调用 `/geo/brand/update` 或 `/geo/brand/delete`；上游成功后才更新或关闭本地投影，上游失败时本地状态保持不变；
- 品牌 Logo 使用独立的 `/geo/brand/update/icon` 和平台 API 更新，不与基础资料 PATCH 合并，避免多次上游调用形成含混的部分成功状态；
- 在腾讯控制台直接新增或改名的品牌，最迟在下一次自动目录核对后创建或更新平台企业；连续两次完整目录核对都缺失的已投影品牌才会被关闭，避免一次不完整响应误删企业；
- 运维同步与自动同步复用同一事务编排、advisory lock、Key 版本校验和连续缺失规则，不形成第二套企业写入逻辑；
- 已删除企业保留关闭状态、BrandID 映射和目录删除标记以承接历史数据，并从正常列表隐藏，后续目录核对不得将其重新创建或激活；
- 企业投影使用 BrandID 摘要生成稳定内部 slug，同时创建同步操作者的首位管理员关系、内部腾讯范围绑定、托管连接占位、品牌映射和默认资源权益；内部绑定不进入管理导航和公开管理 API；
- 本地企业创建、租户侧名称修改和手工品牌绑定均已弃用并返回 410；历史未映射企业不进入平台目录；
- 客户切换为代理商前必须清理显式品牌权限；代理商切换为客户前必须转移企业管理员角色；管理员账户类型不参与切换；
- 代理商可长期有效，也可设置生效和到期时间；未生效或已过期的代理商不能登录、调用 API、成为新企业负责人或接受新企业授权；
- 平台可按目标企业为用户勾选功能模块；模块 allowlist 与角色权限取交集，没有显式记录时继承角色默认权限，空范围表示目标企业全部业务功能关闭；
- 代理商企业额度在新增企业管理员关系时校验，品牌创建额度在调用腾讯创建品牌前校验，腾讯积分额度在余额划拨事务内校验；`null` 不限，`0` 禁止；
- 企业始终保留至少一名有效管理员；固定 TeamID 只在平台腾讯接入中配置，企业端不展示或管理内部范围绑定；
- 创建、启停、授权、移除和统一配置更新写入 `operation_logs`。

## HTTP 资源

- `/api/v1/admin/organizations` 与 `/api/v1/admin/organizations/{organizationId}`：腾讯目录企业集合和企业全景；集合 `POST` 与 `/answerbit-brand` 写入均固定返回 410；
- `/api/v1/admin/organizations/{organizationId}/members`：企业成员关系；
- `/api/v1/admin/users` 与 `/api/v1/admin/users/{userId}`：全局用户和关联范围；
- `/api/v1/admin/answerbit-configuration`：固定 TeamID、统一 Key 与品牌目录的读写资源；
- `/api/v1/admin/answerbit-enterprise-syncs`：使用当前统一凭证立即完成一次腾讯企业目录核对；
- `/api/v1/answerbit/metering/*`：腾讯计量中心的九项读取资源，以及仅平台管理员可调用的 `/quota-purchases` 监控品牌扩容资源；平台“腾讯计量”可跨企业品牌范围读取，企业用户仍受成员和品牌权限约束；
- `/api/v1/admin/answerbit-brands`、`/api/v1/admin/answerbit-brands/{brandId}` 与 `/api/v1/admin/answerbit-brands/{brandId}/icon`：在腾讯官方创建、读取、修改、更新 Logo 和删除品牌，并在需要时维护平台企业投影；
- `/api/v1/admin/answerbit-credentials`：旧多 Key 模型的迁移兼容资源，统一配置启用后禁止写入；
- `/api/v1/admin/publication-provider-configuration`：读取小青蛙 Key 掩码与状态，或验证并加密保存统一 Key；`/api/v1/admin/publication-provider-balance` 读取对应上游余额与算力；`/api/v1/admin/pricing-tier-rules` 维护四级发布加价率和功能积分计费系数；
- 余额、发布、审计与调用沿用各自的 `/api/v1/admin/*` 资源端点。
- `/api/v1/admin/balance-transactions`：分页查询全平台用户积分与余额流水，可按企业、操作用户、资产和操作类型筛选。

字段、方法和状态码以 [OpenAPI 定义](../interfaces/openapi.yaml) 为准；身份不变量见[身份与访问控制](../domains/identity_and_access.md)，统一腾讯接入见[腾讯 AnswerBit 集成](../interfaces/answerbit_integration.md)。

平台计量与自动同步取舍见 [ADR-0011](../decisions/adr_0011_automatic_tencent_directory_and_admin_metering.md)。
