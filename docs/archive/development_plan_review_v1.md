# AI流量推荐官GEO聚合服务平台｜开发方案审查报告 V1.0

> 归档声明：本文是早期方案审查，闸门与待确认项不作为当前实施清单。当前架构与运行状态从[工程文档入口](../index.md)查阅。

审查对象：《AI流量推荐官GEO聚合服务平台｜开发与运营总体方案 V1.0》

## 一、执行结论

**当前闸门：G2——附条件进入开发。**

方案已形成角色、产品模块、Token与媒体余额双账、代理经营和三阶段建设的总体闭环，可以进入交互原型、技术预研和MVP拆解；但还不能直接作为正式开发、固定总价报价或最终验收依据。

进入正式开发前，至少必须冻结：腾讯接口事实、MVP业务规则、角色权限矩阵、Token与余额账务规则、核心状态机、外部媒体履约方式及逐项验收标准。

## 二、做得较成熟的部分

1. 定位明确：不是单一GEO工具，而是GEO能力、媒体履约、代理销售和财务核算的聚合平台。
2. 已主动将“省／市／区代理”抽象成可配置层级，避免把商业组织写死在代码中。
3. 区分Token账户和媒体余额账户，并提出流水、幂等、冲正、批次有效期和先到期先使用，账务意识较强。
4. 已明确线下收款、人工审核入账，首版不盲目建设在线支付和自动结算。
5. 第一阶段围绕一条完整业务闭环，而不是堆砌全部长期功能。
6. 已意识到成本价不能只靠前端隐藏，API也必须执行字段与权限隔离。

## 三、五条闭环判断

| 闭环     | 判断     | 主要说明                                                                  |
| -------- | -------- | ------------------------------------------------------------------------- |
| 客户价值 | 部分闭环 | 能力组合清晰，但品牌客户购买理由、首批客户场景和付费验证指标尚未量化。    |
| 产品使用 | 基本闭环 | 开通、分配、调用、发布、扣费、结果回填已串联；缺状态机和页面级操作定义。  |
| 技术实现 | 部分闭环 | 架构方向合理，但腾讯API、媒体接口、鉴权限流、失败补偿和多密钥规则未核实。 |
| 交易账务 | 部分闭环 | 双账框架成熟，但资金、余额、Token、赠送、冻结、退款和收入确认仍需细化。   |
| 运营交付 | 部分闭环 | 总运营与代理职责已有框架；人工操作SOP、时效、工单和责任界面尚未固定。     |

## 四、开发前必须解决的问题

| R01  | P0   | “腾讯提供API”的实际开放范围、字段、扣费、并发、到期和授权方式未形成正式证据 | 核心功能、成本和架构可能整体返工     | 取得接口文档、商务合同或书面确认，完成最小调用验证                         |
| R02  | P0   | Token究竟是平台计价单位、腾讯积分映射还是预付服务权益，法律与财务口径未统一 | 可能出现错账、退款和合同争议         | 明确名称、兑换规则、赠送属性、退款规则、发票及收入确认口径                 |
| R03  | P0   | 多级代理的客户归属、区域保护、越级关系、退出交接和历史数据归属未确定        | 权限模型和商业合同无法稳定           | 先冻结组织树与客户归属规则，首版建议最多验证两级关系                       |
| R04  | P0   | 角色权限仍停留在概括描述，没有对象×操作×数据范围矩阵                        | 易发生越权、价格泄露和误操作         | 完成平台、代理管理员、代理员工、品牌管理员、品牌成员、财务、运营等权限矩阵 |
| R05  | P1   | GEO任务、生成任务、发布订单、充值申请、退款和调用流水没有状态机             | 前后端、测试和异常处理无法对齐       | 为每个核心对象定义状态、转换条件、责任人和超时处理                         |
| R06  | P1   | 媒体资源是API自动对接、人工代发还是混合履约没有拆开                         | 排期、成本和“返回结果”定义不清       | MVP明确为人工／接口的具体范围，并分别定义证据和时效                        |

## 五、建议的MVP边界

第一阶段应验证“一家总运营中心—一家代理—一个品牌—一套腾讯能力—一类媒体履约”的最短闭环。

### MVP必须

- 组织、用户、品牌和基础RBAC权限；
- 腾讯品牌ID映射及经过验证的最小API能力；
- Token批次、分配、消耗、失败冲正、到期和预警；
- 媒体商品、角色价格、价格快照；
- 线下付款申请、凭证、审核及余额流水；
- 发布订单、余额冻结、成功扣款、失败退款和结果证据；
- 核心操作日志、基础对账和导出；
- 首个代理、首个品牌的端到端验收。

### 条件具备后上线

- 多腾讯密钥自动调度；
- 媒体平台API自动下单与结果回传；
- 多级代理发展下级；
- 自动化经营报表。

### 后续迭代

- 省市区地图、区域保护自动判断；
- 代理升降级、考核和线索分配；
- 自动结算、复杂套餐和经营驾驶舱；
- 高度定制化报表。

## 六、必须补充的产品文档

1. 角色×对象×操作×数据范围权限矩阵。
2. 组织、品牌、用户、腾讯团队和腾讯品牌的关系图及数据字典。
3. Token账户、媒体余额、充值申请、发布订单和退款的状态机。
4. Token批次分配与消耗的守恒规则及异常用例。
5. 价格优先级、锁价、改价、生效期、税费和退款规则。
6. 腾讯API与媒体履约接口清单，包括鉴权、限流、错误码、重试和回调。
7. MVP页面清单、交互原型、接口清单、验收用例和明确的不开发清单。
8. 人工运营SOP：开户、加额、审核、代发、结果回填、退款、投诉和交接。

## 七、代表性验收用例

1. 代理只能查看自身及授权下级品牌；修改请求即使绕过页面直接调用API也必须拒绝。
2. 给品牌分配1000 Token时，若来源批次仅余800，系统拒绝且不生成余额变化。
3. 外部调用超时后重试使用同一幂等号，不得重复扣Token；最终失败产生冲正流水。
4. 修改某媒体价格后，历史订单仍按下单时价格快照结算。
5. 发布失败后，冻结余额完整退回；原冻结、退款及订单可由同一业务号追溯。
6. 上游Token到期时，下游未消耗额度按规则失效，总账与分账汇总一致。
7. 财务加额与退款必须由被授权角色完成，流水不可删除，敏感操作进入审计日志。

## 八、需要Mark确认的关键决策

1. MVP先验证“单级代理”还是一开始就支持两级代理；建议先单级，数据模型保留多级能力。
2. 首版媒体发布采用人工代发、单一平台API还是混合模式；建议先确定一种主履约方式。
3. Token对客户的合同名称及退款属性；在财务与合同口径确认前，不建议直接叫可充值虚拟币。
4. 一个用户能否加入多个品牌；建议数据模型允许多品牌授权，由套餐控制数量。
5. MVP首个行业和首个真实品牌；建议以已签约、能在30天内产生完整数据的客户为样本。

## 九、进入G3开发闸门的条件

- R01—R04全部关闭；
- R05—R09有书面规则并纳入PRD；
- MVP原型和不开发清单经业务、产品、技术三方确认；
- 开发报价按模块、接口依赖和验收结果拆分；
- 至少用一个真实代理和一个真实品牌走通纸面演练；
- 每个核心流程至少包含正常、失败、重复提交、权限不足和余额不足测试。

满足以上条件后，才适合锁定工期、总价和正式开发基线。
