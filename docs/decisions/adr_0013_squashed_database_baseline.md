# ADR-0013：将数据库初始化整理为 v1 当前态基线

- 状态：accepted
- 日期：2026-09-18
- 决策范围：数据库最终结构、Drizzle 迁移历史、发布版本与已部署数据库升级兼容

> 后续状态：v1 继续作为不可修改的结构基线；网页小青蛙凭证与分级定价分别通过 v2、v3 增量迁移加入，符合本文“后续递增 vN”的决策。2026-09-23 对 v1 追加了一条不创建或修改持久对象的会话级 `search_path` 恢复语句，修复 pg_dump 前导空路径导致同一 Drizzle 会话无法继续执行 v2 的全新安装缺陷；该修正不改变基线结构、发布版本或既有数据库。

## 背景

数据库从 0000 到 0044 累积了 45 个 SQL 文件和 45 份快照。简单串联合并虽然减少了文件数量，但仍会先创建后来删除的表、逐次修改字段，并遗留已经没有触发器引用的函数，不能清晰表达当前数据库结构。发布状态同时使用迁移名称和日期式 seed 修订，不利于把本次整理作为稳定的第一版交付。

`packages/db/src/schema.ts` 继续是应用侧 schema 定义，迁移 SQL 继续是实际数据库发布输入。整理必须保证全新安装得到完整结构，也必须让已经完整执行旧 0044 结构的数据库升级时不重复建表、不修改业务数据。

## 决策

1. 使用单一 `packages/db/drizzle/v1.sql` 直接建立当前有效结构：44 张表、26 个枚举、全部约束与索引、8 个仍被引用的触发器函数、8 个触发器、56 条 RLS policy 和当前角色授权。
2. v1 不包含已删除的订单/支付等历史表，不重放中间 `ALTER/DROP`，并移除无触发器引用的 `enforce_billing_order_transition` 与 `protect_billing_refund`。
3. Drizzle journal 只保留一个 `v1` 条目，元数据只保留 `v1_snapshot.json`；基线时间戳继续使用旧 `0044_lively_shard` 的最终时间戳 `1789696960155`。
4. `system_release_state` 的 schema 与 seed 修订统一为 `v1`，后续使用 `v2`、`v3` 递增并按数字比较，不再把迁移文件名或日期作为运行时发布版本。
5. 数据库发布顺序改为 validate → migrate → record-schema-version → seed → rls-check。版本记录步骤先验证 v1 最终结构；对完整旧 0044 数据库清理两个遗留函数并把 schema 记录归一为 v1，对已有更高 `vN` 记录不降级。
6. 已完整执行旧 0000—0044 链或上一版 `0044_baseline` 的数据库按保留时间戳跳过 v1 建表脚本。结构校验通过且迁移账本没有晚于 v1 的记录时，版本记录步骤在事务中把旧 `drizzle.__drizzle_migrations` 收敛为一条使用 v1 SQL 哈希和保留时间戳的记录。未完成旧 0044 的数据库必须先用旧版本补齐迁移，再切换到 v1 发布流程。
7. 后续结构变化以新的增量迁移交付，同时更新对应 `vN` 发布修订；已经发布的 v1 文件不回改。

## 取舍

当前态脚本比历史串联脚本更长，因为完整保留 PostgreSQL 约束、触发器、RLS 与对象 ACL，但每个对象只定义一次，能够直接审阅最终结构。旧的逐步演进过程不再出现在工作树中，需要追溯时使用版本控制历史。

版本记录步骤使旧库可在跳过建表脚本的情况下进入统一 v1 版本，同时通过关键表和最终字段校验避免把明显不完整的历史库错误标记为 v1。完整安全等价性仍由随后的 seed 和 RLS 检查负责。

## 后果

- 全新数据库只有一个 `v1` 迁移记录，schema 与 seed 发布状态均为 `v1`；
- v1 中没有已删除表和无引用函数，Drizzle schema 差异为零；
- 完整旧库升级不重建表、不改业务数据，只清理两个遗留函数并把迁移账本和发布版本归一为 v1；
- release 日志新增 `record-schema-version` 步骤，失败时 Web/Worker 不得发布；
- 新迁移必须同时通过全新库、历史完整库、重复发布和结构等价验证。
